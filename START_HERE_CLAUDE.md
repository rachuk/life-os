# Задание Claude: реализовать Life OS по приложенному PRD

В репозитории нужно **разработать реально работающий веб-продукт Life OS**, а не ограничиваться макетами, архитектурным описанием или списком рекомендаций. Прочитай полностью приложенный `LifeOS_PRD_v1.0_RU.md`: это источник требований, сценариев, схемы данных, критериев приёмки, ограничений и приоритетов.

## Конечная цель
Первый личный пользователь должен открыть Life OS с Mac и iPhone (через веб/PWA), задать график 09:00–18:00, создать задачи, увидеть день/неделю, нажать «Нужно поработать 2 часа» с предпросмотром и подтверждением перестройки, отмечать питание/вес/шаги/тренировки, создавать покупки, принимать план на завтра и получать недельный обзор. По возможности — взаимодействовать через Telegram и голосовые/фото. Бизнес-логика должна быть настоящей, с хранением и тестами.

## Порядок выполнения (важно)
1. Изучи текущий репозиторий. Если пустой — создай Next.js App Router + TypeScript (strict) + Tailwind, качественный мобильный интерфейс, PWA.
2. Реализуй Supabase Auth, Postgres, миграции, RLS, приватные файлы. Если нет ключей/настроенных облачных сервисов, обеспечь локальный путь и ручной рабочий режим. Никогда не вставляй секреты в код.
3. Построй **P0 вертикально**: онбординг → главная → задачи → календарь → extra-work preview/commit → привычки и измерения → журнал событий → напоминания → вечерний/недельный обзор. Каждая кнопка должна работать или честно показывать, что интеграция не настроена.
4. Реализуй Telegram pairing + webhook + действия через кнопки, если предоставлены credentials. Отдельно реализуй изолированный `AIProvider` для транскрипции, распознавания команд и фото с подтверждением действий. Без AI ключа система должна оставаться полезной.
5. Добавь недельный список покупок, базовый журнал тренировок, XP/виртуальный фонд желаний, если не затрагивается качество P0.
6. Напиши критические unit/integration/E2E тесты, особенно конфликты планировщика, DST Europe/Lisbon, идемпотентность уведомлений, приватность двух аккаунтов. Запусти `lint`, `typecheck`, `test`, `build` и исправь ошибки.

## Жёсткие требования к качеству
- Никаких фиктивных подтверждений, ненастоящей синхронизации, фальшивых скриншотов пользовательской статистики, моковых данных вместо сохранения в реальной БД (исключение — явно подписанный demo mode).
- Не делай общедоступный SaaS/платежи/Stripe/корпоративные интеграции. Архитектура должна быть SaaS-ready через `user_id`, RLS и конфигурацию.
- Рабочая зона 09:00–18:00 в будни блокируется; еда допускается в перерывах; сон и питание не вытесняются переработкой автоматически.
- Никакого жёстко зашитого подъёма в 08:30; время утренних дел пользователь выбирает сам. Зал предпочтительно 21:00–22:00, но это настройка.
- Голосовые на русском/украинском/английском; все результаты AI — только предложения, сомнительные значения требуют подтверждения. Фото тела — исключительно opt-in.
- Сохраняй данные и показывай ошибки, реализуй честный fallback при отсутствии API ключей.
- Не проси дополнительных уточнений об уже обсуждённых требованиях; если параметр не известен, добавь настройку и безопасный нейтральный default.
- Держи интерфейс на русском; современный минималистичный дизайн, удобный на iPhone и Mac.
