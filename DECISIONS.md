# Архитектурные решения Life OS v1

Документ фиксирует, что выбрано, почему, и чем за это заплачено. Источник требований — `LifeOS_PRD_v1.0_RU.md`.

## 1. Инфраструктура: обычный PostgreSQL вместо Supabase, self-hosted вместо Vercel
**Решение владельца (1 ноября 2026):** без Supabase и без платных сервисов, кроме ИИ при необходимости.
- **БД** — PostgreSQL 15+ (локально Homebrew, в проде контейнер `postgres:17-alpine` со своим томом, отдельно от Nivi и Astudy на том же сервере).
- **Авторизация** — собственная: email + пароль (`scrypt` из стандартной библиотеки Node), сессии в таблице `sessions` (в cookie лежит только случайный токен, в БД — его sha256), ограничение частоты попыток входа, регистрация закрыта (`pnpm user:create`). Сброс пароля — консольная команда: почтовый сервис для одного пользователя избыточен.
- **Хранилище файлов** — закрытая папка на диске (Docker-том), отдача только через авторизованный маршрут с подписанной ссылкой на 5 минут. Модуль `src/server/storage/files.ts` спроектирован так, чтобы позже подключить S3-совместимое хранилище (например, MinIO).
- **Cron / очередь** — свой worker (`pnpm worker`, отдельный контейнер), плюс `POST /api/internal/notifications/process` под `CRON_SECRET` как запасной вход для системного cron.
- **Хостинг** — Docker Compose на `netcup` за уже работающим Caddy (автоматический HTTPS), адрес `life.astudypro.com`. Лимиты памяти на контейнерах, чтобы не мешать соседним проектам.
**Компромисс:** больше своего кода (авторизация, хранилище), зато нет зависимости от поставщика и ежемесячной платы.

## 2. RLS без Supabase
Все пользовательские таблицы имеют `user_id` и политику `user_id = app.current_user_id()`. Пользовательский код выполняется в транзакции `SET LOCAL ROLE lifeos_user` + `set_config('app.user_id', …)`, поэтому изоляцию двух аккаунтов обеспечивает сам Postgres, даже если в запросе забыли фильтр. `withSystem` (владелец таблиц, обходит RLS) используется только там, где без него никак: вход, проход worker'а по всем пользователям, маршрутизация Telegram `chat_id → user`, очистка просроченных файлов. Колонка `users.password_hash` и таблица `sessions` для пользовательской роли недоступны. Это проверено тестами.
**Компромисс:** каждая операция — короткая транзакция с двумя служебными запросами (около 1 мс). Это готовность к SaaS без переписывания.

## 3. Детерминированный планировщик, ИИ только советует
`src/domain/planner/*` — чистые функции без ввода-вывода: настройки → шаблоны → развёртывание недели (идемпотентно по `origin_key`) → предпросмотр переработки → состояние «Сейчас». ИИ не участвует в разрешении конфликтов.
- **Классы событий:** fixed / protected / required_movable / flexible / buffer.
- **Сон** — жёсткая граница вечера: никогда не сокращается, вместо этого показывается конфликт и вариант «Сократить до N».
- **Еда** сдвигается только внутри своего окна (`flex_window`). Если сдвинуть нельзя, работа прерывается на приём пищи (так решено противоречие в примере §5.4: «ужин 19:30 при работе 18:00–20:00»).
- **Тренировки и свои проекты** переносятся позже в тот же день (не раньше конца переработки + 15 мин + дорога) или на другой день той же недели (тренировки — не подряд, если есть выбор). Если места нет — явный риск для недельной цели, и применение требует подтверждения.
- **Без времени задним числом:** если 18:00 уже прошло, блок начинается «сейчас».
- **Конкурентность:** версия плана на неделю (`plan_versions`) + advisory-lock + отпечаток предпросмотра; устаревший предпросмотр → `409 PLAN_VERSION_CONFLICT` с новым предпросмотром. У отдельных событий своя `revision`.
- **История и отмена:** `plan_changes` хранит from/to каждого изменения, «Отменить» восстанавливает события и пересчитывает напоминания.

## 4. Время
Моменты хранятся в `timestamptz` (UTC), интерпретация — по IANA-поясу профиля (Luxon). Локальная дата — строка `YYYY-MM-DD`; Postgres-типы `date`/`time` намеренно не превращаются в JS `Date`. Работа в 09:00 и зал в 21:00 остаются локальными через переходы DST (тесты на 25.10.2026 и 28.03.2027). Ночь, начавшаяся после полуночи, относится к «вчерашней ночи» и показывается на экране «Сегодня».

## 5. Напоминания
Outbox с идемпотентным `message_key = user|event|type|scheduled_at|channel`. Worker:
1. синхронизирует ожидаемые напоминания (лишние отменяет, недостающие создаёт);
2. отправляет те, чьё время пришло;
3. для важных напоминаний ставит один повтор: его ключ не содержит времени, поэтому больше одного физически невозможно;
4. отменяет повтор, если пользователь ответил в любом канале;
5. пропускает протухшие (>30 мин после простоя), часы тишины и сверх дневного лимита.

Канал «в приложении» работает всегда. Push используется только если Telegram не подключён — чтобы не дублировать.

## 6. Ввод текста и ИИ
Единый контракт «предлагаемых действий» (`src/domain/capture/schema.ts`, zod). Удаления и денежных переводов в нём просто нет.
- Без ключей работает **детерминированный разборщик** для русского, украинского и английского: относительные даты, неоднозначности → «проверь».
- `AIProvider` говорит с любым OpenAI-совместимым API: OpenAI, локальная Ollama, whisper-сервер. Ответ ИИ проверяется схемой и дополнительно сверяется по датам с разборщиком на правилах; расхождение → требуется подтверждение.
- Отправка во внешний ИИ — только по отдельному согласию (текст / голос / фото), есть дневной лимит запросов.

## 7. Что сознательно отложено
- Публичная регистрация, тарифы, оплата (PRD: не делать в P0).
- Нативный HealthKit (нужно нативное приложение; в P0 — ручной ввод и скриншот).
- Drag-and-drop в недельном плане (PRD: опционально). Есть список, формы и перенос.
- Офлайн-запись с очередью синхронизации. Есть офлайн-просмотр последнего плана и явная ошибка при отсутствии сети.

## 8. Известные ограничения
- Распознавание фото локальной моделью на сервере без GPU невозможно. Варианты: Ollama на Mac (через Tailscale), платный API или ручной ввод (работает всегда).
- Push на iPhone работает только из PWA, добавленной на экран «Домой» (iOS 16.4+), и не гарантирует доставку. Для пробуждения нужен будильник iPhone.
- Telegram-бот не даёт сквозного шифрования (особенность Telegram-ботов).
- Резервные копии БД (`deploy/backup.sh`, 14 дней) содержат данные удалённого аккаунта, пока копии не устареют.
